# How the runtime works

Naughty Bear's executable (`Default.xex`) is translated ahead of time by XenonRecomp into
C++ (`generated/ppc`): every PowerPC function becomes a C++ function operating on a
`PPCContext` (the registers) and a 4 GB block of host memory that stands in for the
console's address space. The runtime in `src/` provides everything the executable expects
from the console: the kernel and XAM functions it imports, and the hardware it talks to
(GPU, XMA audio decoder). Graphics are described in [d3d_map.md](d3d_map.md).

## Recompilation

`tools/recompile.sh` builds a patched XenonRecomp and runs it with `config/NB.toml`. The
configuration lists the jump tables found by `tools/nbanalyse/nb_switch_tables`
(`config/NB_switch_tables.toml`) and data the analyzer must not treat as code (the
exception handler records in front of some functions).

Patches to XenonRecomp (`patches/XenonRecomp/`):

| Patch | Why |
|-|-|
| 0001, 0002 | Switch cases and fall-throughs that leave the function become tail calls |
| 0003 | Instructions Naughty Bear uses that XenonRecomp didn't support, and half-float conversions |
| 0004 | Branches to the next instruction don't end a function during analysis |
| 0005 | Integer division by zero yields 0 instead of trapping, as on the PowerPC |
| 0006 | `switch` statements index with the low 32 bits of the register |
| 0007 | `mftb` (the timebase) runs at the console's 49.875 MHz, derived from the host clock |

The timebase patch matters: the game measures time with `mftb` against
`KeQueryPerformanceFrequency` (49.875 MHz). With the host's cycle counter the game's clock
ran about 60 times too fast, and its loader, which works in time slices, took minutes to
load a level.

Functions can be replaced from `src/`: the generated code calls every function through a
weak symbol `sub_XXXXXXXX`, and a `PPC_FUNC(sub_XXXXXXXX)` in the runtime overrides it
(usually calling the original `__imp__sub_XXXXXXXX` around its own work). Imports are
implemented with `GUEST_FUNCTION_HOOK`; imports the runtime doesn't implement get logging
stubs generated by `tools/gen_import_stubs.py`.

## Startup

`src/main.cpp` finds the game (`Default.xex` in a `game` folder next to the executable,
in the working directory or in a parent folder), sets up the kernel (heaps, the `game:`
and `D:` roots), loads the executable (decrypting and decompressing it), opens the window,
starts the audio, XMA decoder and input, and runs the game's entry point on its own thread.
The main thread handles SDL events.

## Memory

| Range | Use |
|-|-|
| `0x00020000-0x40000000` | Runtime heap: kernel objects, thread blocks, `XAlloc` |
| `0x40000000-0x7FEA0000` | `NtAllocateVirtualMemory`, where the game's own heaps live |
| `0x7FEA0000` | The XMA decoder's registers |
| `0x82000000-0x834A0000` | The executable's image |
| `0xA0000000-0xC0000000` | Physical memory (`MmAllocatePhysicalMemoryEx`), 512 MB like the console |

Physical memory is kept to one 512 MB window so that a GPU address (its low 29 bits)
maps back to exactly one allocation; it uses an exact-size allocator rather than o1heap,
whose power-of-two rounding would not fit.

## Threads and synchronization

Guest threads (`ExCreateThread`) are host threads with their own `PPCContext` and stack;
`ExTerminateThread` unwinds back to the thread's start. Events, semaphores, mutants and
timers are host objects behind the kernel handles and dispatcher headers. Waits support
timeouts, `WaitForMultipleObjects` in both modes, and alertable waits: APCs queued with
`NtQueueApcThread` run when the target thread waits alertably.

## Files and saves

`src/kernel/io/nt_file.cpp` maps the game's paths (`game:\`, `D:\`, save roots) to host
files. Reads can be asynchronous: requests complete at once and are reported through the
request's event or an I/O completion port (`NtCreateIoCompletion`, `NtRemoveIoCompletion`),
which the game's streaming threads use.

Saves (`src/kernel/xam_content.cpp`): the game picks a storage device (one hard drive is
offered) and creates save containers; each container is a folder under `save/`, with its
metadata stored alongside, so saves persist. The user is an offline profile; profile
settings read as "not set", so the game uses its defaults.

## Data packages

The game's data is in `lu/*.lu` packages: a header listing the package's dependencies and
assets, then the payload, stored as is or as 1 MB chunks compressed with XMemCompress
(LZX). `src/kernel/packages.cpp` reads them for the shader precache, decompressing with
the game's own recompiled `XMemDecompress` (see [d3d_map.md](d3d_map.md#shaders)). The game
itself loads them through its own code. `*.cu` files list audio streams.

## Audio

The game mixes audio with XAudio2, statically linked. Its render client is called every
256 samples (48 kHz) by an audio thread (`src/apu/driver/sdl2_driver.cpp`) and hands back
5.1 frames, which go to SDL (downmixed to stereo unless `NB_SURROUND=1`).

Most sounds are XMA, which the console decodes in hardware. `src/apu/xma.cpp` emulates
the decoder: contexts (64 bytes each, layout as documented by Xenia) live in one array
whose address is published in the decoder's registers; the library fills in input
buffers (2 KB packets), an output ring and loop points, and writes bit masks to the Kick,
Lock and Clear registers. The functions that write those registers are hooked so a kick is
decoded before the library continues, as with the hardware (a polling thread is the
fallback). Decoding uses FFmpeg's XMA2 decoder on whole packets, built from
`thirdparty/FFmpeg` with a patch so a single stream isn't held back by 4096 samples.

## Input

`src/hid/hid.cpp` reports player 1's controller from SDL: the most recently used game
controller plus the keyboard. Controllers already connected at startup are opened
explicitly (their connection events arrive before the input handler exists). Rumble
requests are applied from the main loop: calling SDL's joystick functions from the game's
threads deadlocked with SDL delivering controller events.

## Graphics hardware

The game's Direct3D library still runs: it builds command buffers for a GPU that isn't
there. `src/gpu/headless.cpp` makes it believe the GPU keeps up (completes fences, moves
the ring buffer read pointer, raises the 60 Hz vertical blank interrupt), while the
renderer (`src/gpu/video.cpp`) mirrors the draws with Vulkan. See
[d3d_map.md](d3d_map.md).

## Analysis tools

`tools/nbanalyse` has the tools used to find things in the executable: `disas`,
`funcinfo`, `xrefs` (callers of an address), `callgraph` (per function: callers, imports,
GPU packets built), `find_bytes`, `peek`, `imports`, `eh_handlers`, `bctr_survey`,
`pm4scan` and `nb_switch_tables`. A build configured with `-DNB_TRACE_D3D=ON` logs the
game's calls into its Direct3D library.
